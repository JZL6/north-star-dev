# 基于文档的需求澄清

Explore 后存在需要用户决定的问题时读取。目标是让需求、验收和关键设计足以安全推进，同时把决定写进权威文档。

## 事实与决策

- **事实由 Agent 查找**：现有行为、代码入口、接口、测试、配置、历史、文档内容和工具能力。可以派发调查 subagent，并继续处理不依赖该事实的问题。
- **决策由用户作出**：业务目标、范围取舍、验收含义、冲突来源的取舍、难以逆转的架构选择和外部协作承诺。

用户是新员工时，先用业务语言解释事实和影响。不要让用户选择测试框架、文件路径或内部函数等可从仓库确定的事项。

## 问题 frontier

把问题组织为依赖树。每轮只询问前置条件已经解决的问题 frontier；依赖本轮其他答案的问题留到下一轮。一次列出整个 frontier，减少往返。

每题包含：

1. 一句明确问题。
2. 已确认事实与来源。
3. 2–3 个真实可行选项及影响；没有离散选项时说明需要的输入。
4. Agent 的推荐答案及理由。
5. 不回答会阻塞哪个产物或 Issue。

小改动若目标、验收和 seam 已从请求及仓库明确，记录“无需用户决策”并继续。不得为了执行 Grill 仪式提出无价值问题。

## 必问条件

- 同一句需求有不同业务结果或验收含义。
- 代码、文档和用户陈述冲突，且选择会改变行为。
- 新行为会扩大 Epic 范围、破坏兼容或改变 Project 不变量。
- 需要选择难以逆转的数据、接口、部署或安全策略。
- 无法构造可判断对错的验收 oracle。
- 需要用户提供凭据、权限、外部数据或组织决定。

## 可推迟条件

不阻塞当前 tracer bullet、可逆且有安全默认值的问题可以进入 Epic Open Questions。记录其影响、触发条件和负责消除的 Issue。不能把当前实现必需的决定伪装成“以后再说”。

## 文档落点

- 项目长期领域词汇或不变量：Project Spec 或项目现有术语表。
- 难以逆转、令人意外且经过真实取舍的决定：ADR。
- 当前需求的范围、验收和跨 Issue 设计：Epic Spec。
- 当前 Issue 的局部设计与测试 seam：Delta-Design。

一个决定只有一个权威位置，其他文档以 ID 和路径引用。每轮答案落盘后重算 frontier；完成条件达到时自动进入 Epic/Issue，不再询问是否继续。
