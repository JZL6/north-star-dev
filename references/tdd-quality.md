# TDD 与测试深度

创建 Delta-Spec、Delta-Design、Test Charter、测试或 Verification 时读取。测试目标是发现错误并稳定表达行为，覆盖率只作为辅助信号。

## 1. Test Charter

写测试前，在 Delta-Design 或 Verification 中建立 Test Charter：

| 内容 | 必须回答 |
|---|---|
| 行为 | 本 Issue 改变哪些可观察行为，对应哪些 Requirement/Acceptance ID？ |
| 风险 | 最可能、影响最大、最难发现的错误是什么？ |
| seam | 从哪个公共 interface 观察行为？为什么这是最高且稳定的 seam？ |
| oracle | 预期结果来自规格、协议、已知样例还是独立模型？ |
| 层级 | 哪些用单元、模块/集成、契约或端到端测试，为什么？ |
| 维度 | 哪些边界、状态、失败、并发、兼容和资源场景需要覆盖或明确不适用？ |
| 环境 | 如何控制时间、随机、I/O、外部服务和测试数据，使结果可复现？ |

seam 是调用者与测试共同使用的 interface。优先使用现有最高层 seam；只有现有形状无法表达目标行为时才新增 seam，并在 Delta-Design 记录理由。内部 seam 可以存在，但不因测试需要暴露到公共 interface。

## 2. 测试深度矩阵

按风险选择维度，不要求每项机械产生测试。高风险维度必须标记 `covered` 或 `not_applicable + 理由`。

- 主路径与关键业务分支。
- 输入等价类、上下界、空值、长度、数值溢出和编码。
- 状态转换、非法转换、顺序、重复调用和幂等性。
- 错误传播、超时、取消、重试、部分成功、恢复和降级。
- 并发、重入、竞态、乱序、背压和资源耗尽。
- 生命周期：初始化、关闭、重启、持久化恢复和清理。
- 数据、协议、配置和版本兼容。
- 权限、信任边界和敏感数据处理。
- 日志、指标、错误码及调用者可观察诊断。

网络或状态机代码重点检查分片/粘连、部分读写、连接中断、重连竞态、定时器、重复消息、乱序和资源释放。其他领域按实际风险替换这些场景。

## 3. 好测试的判据

- 测试名描述能力或业务行为，断言通过公共 interface 观察结果。
- 预期值来自独立来源：明确规格、协议常量、手算样例或独立参考模型。测试不能复制生产算法重新计算答案。
- 一个测试聚焦一个逻辑行为；失败信息能指出哪条规格失效。
- 内部重构不改变行为时，测试保持不变。
- 对关键断言做敏感度检查：如果返回值、状态或错误被故意改错，测试应失败。工具可用且成本合适时使用 mutation testing。
- 测试确定、可重复，明确管理时钟、随机数、并发调度和外部资源。

mock 用在真正外部 seam：第三方 API、不可控远端、时间/随机或成本过高的系统资源。优先使用本地真实实现或 in-memory adapter；避免 mock 自己的内部模块、私有方法、调用次数和实现顺序。

## 4. Red → Green slice

一次推进一个可观察行为：

1. 从未满足的 Acceptance/Check ID 选择最小 tracer bullet。
2. 写一个测试，运行并确认 red；记录失败信息和“为什么这是预期失败”。编译失败只有在当前 slice 明确引入新 interface 时才可作为初始 red。
3. 若测试意外为绿，检查行为已存在、测试无效或 oracle 错误；解决后再实现。
4. 写通过该测试所需的最小代码，运行目标测试和直接受影响测试。
5. 绿灯后清理刚触碰范围内的命名、重复和局部结构，保持测试绿色；结构性重构进入工程健康 Gate。
6. 更新 Task 与追踪表，再选择下一 slice。不要先批量写完所有测试或提前实现未来 slice。

性能、安全、迁移、调查或纯重构可使用基准、静态分析、characterization tests、故障注入或可复现实验代替标准 red/green，但仍需先定义失败/成功判据。

## 5. 分层测试策略

测试层级由反馈速度和风险决定，不按数量配额：

- TDD 内环使用能最快稳定表达行为的 seam。
- Issue Gate 覆盖完整 Delta-Spec、相关模块和契约。
- Integration Gate 验证跨模块交互、真实 adapter 或关键数据路径。
- Epic Gate 验证业务流程、兼容、迁移和发布风险。

相同风险已经在更高且稳定的 seam 充分覆盖时，删除或避免增加与实现耦合的低层重复测试。保留低层测试只因它能提供独立、更快或更精确的故障定位价值。

## 6. Verification Gate

通过前必须满足：

- 每个 Acceptance ID 有测试/证据，或有明确豁免依据。
- Test Charter 的高风险维度均有处置。
- 至少观察过目标行为的可信 red，且 green 不是通过弱化断言、删除测试或放宽门禁获得。
- 关键 oracle 独立，测试能对典型错误保持敏感。
- 测试没有大量绑定内部结构或重复已有覆盖。
- 覆盖率变化已解释；高覆盖率不能抵消未测的高风险行为。
- 独立 reviewer 审查测试设计，而不只检查测试是否通过。
