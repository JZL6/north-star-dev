# Issue 模板

> Issue 是推进粒度，不是执行粒度。一个 Issue 内含调查、设计、TDD 执行、验证完整闭环。

---

```markdown
# Issue — [Issue 名称]

## 1. 基本信息

- **Issue ID**：issue_XXX
- **轮次**：第 0/1/2/3 轮
- **层次**：L0 / L1 / L2 / L3 / 跨层
- **模块**：[模块名称]
- **创建时间**：YYYY-MM-DD
- **状态**：pending / in_progress / completed / blocked

## 2. 任务目标

[一句话描述这个 Issue 要达成什么目标]

## 3. 适用约束

从 Project Spec 和 Epic Spec 中筛选与本 Issue 相关的约束：

- [架构约束 1]
- [编码规范 1]
- [测试规范 1]

## 4. 前置依赖

- 依赖的 Issue：[Issue ID 列表，无则写"无"]
- 交接要点：[从前序 Issue 需要了解的关键点]

## 5. 调查任务（如需要）

如果现有实现不明确，先做调查：

- [ ] 调查 [模块/接口] 的现有实现
- [ ] 确认 [行为/边界] 的当前状态
- [ ] 记录调查结论

## 6. 局部设计（如需要）

如果 Issue 内设计未明确，先形成局部设计：

### 6.1 设计方案
[描述本 Issue 的设计方案]

### 6.2 接口定义
[新增或修改的接口]

### 6.3 数据结构
[新增或修改的数据结构]

## 7. 测试用例 / 任务清单

按执行顺序排列，每条用例 Given-When-Then 格式：

| 序号 | 用例 ID | 标题 | Given-When-Then | 优先级 |
|---|---|---|---|---|
| 1 | TC-001 | [标题] | Given [前置条件] When [操作] Then [预期结果] | P0 |
| 2 | TC-002 | [标题] | ... | P0 |
| 3 | TC-003 | [标题] | ... | P1 |

## 8. TDD 与重构执行约束

### 8.1 每条用例后
- 红灯：写测试 → 确认失败
- 绿灯：写最小实现 → 确认通过 → 回归
- 微重构：命名/去重/简单拆分，需要就做

### 8.2 本 Issue 完成后
- 局部重构：模块内重构，需要就做
- 不适合现在做的，记入"本 Issue 待重构清单"

## 9. 验收标准

- [ ] 所有用例通过
- [ ] 全量回归测试通过
- [ ] 覆盖率达到门禁要求
- [ ] 代码符合编码规范
- [ ] 微重构已完成或记入待重构清单
- [ ] 交接清单已产出

## 10. 执行记录（subagent 填写）

### 10.1 完成情况
- 状态：成功 / 部分完成 / 失败
- 完成用例数：X / Y
- 问题：[遇到的问题]

### 10.2 代码变更
- 新增文件：[列表]
- 修改文件：[列表]

### 10.3 测试变更
- 新增测试文件：[列表]
- 修改测试文件：[列表]

### 10.4 交接清单
- 做了什么：[总结]
- 产出：[关键产出]
- 注意事项：[后续需要注意的]
- 已知问题：[未解决的问题]
- 下一步建议：[建议]

### 10.5 待上浮项
超出本 Issue 范围、需要上浮到 Epic 或 Project 级的问题：

| 问题 | 级别 | 说明 |
|---|---|---|
| [问题] | Epic / Project | [说明] |

### 10.6 本 Issue 待重构清单
当前未做、需要后续处理的重构点：

| 重构点 | 级别 | 说明 | 计划处理时机 |
|---|---|---|---|
| [重构点] | 局部 / 全局 | [说明] | [下一个 Issue / 本轮结束 / 下一轮] |

### 10.7 自测结果
- 全量测试结果：[通过/失败 + 详情]
- 覆盖率：[语句覆盖率 / 分支覆盖率]
- 是否过门禁：是 / 否
```

---

## 填写说明

### 主 Agent 填写部分
- 第 1~9 节：主 Agent 创建 Issue 时填写
- 调查任务和局部设计：如果设计已明确，可以留空或写"已在 Epic Spec 中明确"

### subagent 填写部分
- 第 10 节：subagent 执行完成后填写
- 执行记录要完整，便于主 Agent 验收和后续 Issue 交接
