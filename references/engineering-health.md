# 项目适配与持续重构

编写 Delta-Design、实现代码、执行 Issue Gate 和 Epic 关闭检查时读取。目标是让局部改动增强现有项目，而不是堆出一个局部优秀但全局重复的实现。

## 1. Project Fit Gate

编码前完成复用与职责扫描：

1. 用领域词、行为、接口名、错误码和测试场景搜索整个相关代码库。
2. 找到谁当前拥有该业务不变量、状态和数据；画出调用者、依赖方向和公共 interface。
3. 对比现有能力与 Delta-Spec：可直接复用、应扩展、需要 adapter，还是确实需要新模块。
4. 检查其他开放 Issue/Epic 是否正在构建同一能力或修改同一 seam。
5. 在 Delta-Design 记录选择及被否决方案。没有搜索证据的“新建模块”不能进入实现。

同一不变量应有一个权威实现。名称不同但语义相同仍是重复；代码文本不同也可能构成语义重复。

## 2. 深模块与 seam

- **深模块**以小 interface 隐藏大量行为，让调用者获得 leverage，让维护者获得 locality。
- **deletion test**：设想删除新模块。若复杂度消失，它可能只是转发层；若复杂度回流并散落到多个调用者，它在集中复杂度。
- interface 包括签名、错误、顺序、配置、不变量和性能约束。新增方法前检查能否扩大现有入口的深度。
- 一个生产 adapter 加一个真实测试替身可以形成有价值的 seam。只有一个实现且没有变化需求时，新增 interface 往往只是猜测性间接层。
- 测试通过与调用者相同的 interface，内部 seam 保持内部。

优先“先让改动容易，再做容易的改动”：若现有结构无法安全容纳行为，先创建有行为保护的 prefactor Issue。prefactor 只改善 seam 或 locality，不偷带新功能。

## 3. Change Budget

Delta-Design 在实现前声明：

- 预计触及的模块和公共 interface。
- 新增/删除的模块、依赖、配置、数据和 adapter。
- 允许的兼容、迁移和临时代码。
- 预期代码形态和明确不做的扩展点。

实施中出现新公共 interface、新依赖、跨越额外职责边界、明显超出预期的代码量或多个新抽象时暂停扩写，重新执行 Project Fit。必要工作仍在 Issue 目标内则更新设计；可独立验收或改变目标的工作拆成新 Issue。

避免 speculative generality：不为假想未来场景增加参数、hook、通用框架或第二套模型。新抽象至少要隐藏真实复杂度、统一现有重复，或服务当前明确的多个使用者。

## 4. 重构节奏

| 时机 | 范围 | 目标 |
|---|---|---|
| 每个 green 后 | 当前 slice 触及范围 | 命名、显式重复、局部可读性，保持测试绿色 |
| Issue 实现结束 | 受影响模块 | locality、interface 深度、重复、错误模型、测试 seam |
| 审查修复 | finding 指向的范围 | 修复规格、架构、测试或维护性问题 |
| Epic 阶段/关闭 | 跨 Issue 热点 | 语义重复、公共 interface 漂移、临时代码和依赖扩散 |

结构性重构不塞进 red/green 的最小实现。它需要已有行为保护、独立 Task 或 Issue、明确 fixed point 和验证。宽范围机械迁移使用 expand → 分批 migrate → contract，使中间状态保持可构建或在明确的集成 Gate 验证。

重构新 seam 后，新测试应从新 interface 覆盖行为；没有独立定位价值的旧浅层测试应替换，避免一层新测试叠一层旧测试造成维护债。

## 5. Comment Quality Gate

注释的职责是保存代码本身难以表达、对未来维护者重要的知识，而不是把语句翻译成自然语言。没有注释数量或覆盖率目标；应先用命名、类型、模块边界、错误模型和测试表达“做什么”。

值得保留或新增的注释通常解释：

- 业务不变量、协议陷阱或看似奇怪但必须保持的兼容行为。
- 并发、生命周期、内存所有权、顺序或故障恢复约束。
- 非显而易见的取舍，以及为什么没有使用更直观的方案。
- 安全/隐私边界、审计要求和禁止简化的原因，但不得写入 secret 或敏感样本。
- 临时 workaround 的根因、关联 Issue 和可验证的删除条件。

以下内容必须修复：

- 逐行复述赋值、分支、循环或函数名的“代码翻译器”注释。
- 与当前实现、规格、单位、边界或错误行为冲突的陈旧/错误注释。
- 被注释掉的旧代码、无理由的历史叙述、复制到多处后会漂移的规则说明。
- 没有关联 Issue、责任归属或移除触发条件的 TODO/FIXME/workaround。
- 用长注释掩盖命名、职责或控制流问题；应先改善代码结构，再保留真正的 why。

实现者在每个 green 后清理触及范围的注释；Issue Verification 对 diff 中新增/修改/邻近的关键注释做语义核对；Quality reviewer 将误导性注释按其风险定级。会导致错误修改、安全误解或协议破坏的注释可以是 major/blocker，单纯冗余通常是 minor。不要为了通过门禁批量删除仍承载必要背景的注释。

## 6. 技术债处置

每项债务记录：证据、影响、为何当前不处理、处理触发条件、目标位置和责任归属。处置只有四种：

- 当前修复：不修就不能满足 Issue/Epic 退出条件。
- 阻塞性 prefactor：先解决才能安全继续后续 Issue。
- 独立后续 Issue：边界明确，延后不会让当前实现失真。
- 明确接受：收益不足以覆盖成本，记录原因和重新评估条件。

没有触发条件或责任归属的“以后重构”视为未处置。债务累计改变 Project 不变量、公共接口或多个 Issue 时必须上浮，不能隐藏在 Closure 自由文本。

## 7. Issue 与 Epic 健康检查

Issue 关闭前检查：

- 新能力是否与现有能力语义重复。
- 新模块是否通过 deletion test，interface 是否比隐藏的复杂度更小。
- 代码改动是否仍匹配 Delta-Design 和 change budget。
- 是否存在未使用代码、只转发抽象、重复数据模型、散落配置或跨职责修改。
- 测试是否重复绑定旧实现，而不是保护稳定行为。
- 注释是否解释必要的 why，且没有逐行翻译、陈旧陈述、注释掉的代码或无退出条件 TODO。

Epic 关闭前跨 Issue 搜索相同领域词、行为、数据结构、错误策略和 helper。比较各 Issue 的 Delta-Design 与 Closure，合并重复实现，处理临时代码，更新 Project/Baseline 的权威所有权和 seam。
