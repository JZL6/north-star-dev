# 人类审批与生产发布边界

在范围豁免、高风险设计、不可逆操作或生产发布相关工作中读取。Agent 负责准备证据和执行已授权的有界动作；Agent 不是业务、风险、安全或生产发布责任人。

## 1. 审批触发器

命中以下任一项时，必须创建 Approval 记录：

- 改变或豁免目标、范围、验收、Project 不变量、公共 API/协议或外部承诺。
- 数据模型/Schema 迁移、兼容性破坏、数据删除或其他难以逆转的操作。
- 接受 security/privacy 残余风险，改变数据分类、权限、信任边界、保留或外部传输。
- 使用生产凭据、修改生产配置/基础设施、执行生产迁移、发布、回滚或面向真实用户的开关切换。
- 仓库或组织规则明确要求人工审核的其他动作。

代码 review、测试 PASS、用户要求“实现/完成”都不等于上述审批，也不授权生产操作。

## 2. 审批权限与记录

从仓库、团队制度或用户明确说明中解析审批角色，不猜测人员或权限。权限来源不明确时标记 `approval_blocked`，向用户说明需要哪类责任人决定。

使用 [../assets/approval-matrix-template.md](../assets/approval-matrix-template.md) 记录：

- 稳定 Approval ID 和触发原因。
- 决策范围、目标源码/文档修订及不可超出的边界。
- 决策：`pending / approved / rejected / expired / superseded`。
- 有权角色、实际批准人（已知时）、来源、时间、条件和到期时间。
- 评审证据、残余风险、回滚条件和被替代 Approval ID。

批准必须能追溯到用户或组织的权威记录。Agent 不能填写虚构批准人、把沉默当批准、批准自己的风险豁免，或把旧修订的批准自动套用于新范围。范围/风险/目标修订改变后重新判断批准是否仍有效。

## 3. 开发完成不等于发布完成

状态必须分开：

```text
implemented → verified → reviewed → accepted_for_code
                                    ↓ 独立发布准备
                              ready_for_release
                                    ↓ 明确人工授权
                                  released
```

Issue 可以在没有生产授权时完成代码交付，但必须明确为 `accepted_for_code` 或“待发布”，不能声称已上线。若 Issue 退出条件本身要求真实生产发布，则缺少授权时状态为 `release_blocked`，不得关闭为 accepted。

## 4. Release Gate

任何生产变更前，主 Agent 必须重新核对当前修订和 Approval 状态，并提供：

1. 发布对象、版本、环境、影响面和明确非目标。
2. 构建/测试/安全/迁移证据及其源码修订。
3. 配置和 secret 获取方式；不得在文档或对话中暴露值。
4. 迁移顺序、兼容窗口、备份/恢复和失败原子性。
5. 分批/canary/feature flag（适用时）、停止指标和回滚触发条件。
6. 日志、指标、告警、业务检查和发布后验证负责人。
7. 有效的 Release Approval ID，以及授权明确覆盖本次环境、修订和动作。

生产 mutation 必须获得紧邻执行时点的明确授权；早期架构批准或 PR approval 不能替代。没有明确授权时只生成发布计划、命令草案和证据包，状态为 `release_blocked`，不执行部署、迁移、配置写入、开关切换或回滚。

## 5. 执行与停止条件

- 每次外部/生产动作只执行批准范围内的最小步骤，检查前置条件和返回结果。
- 出现版本漂移、未知数据、指标越界、权限异常、计划外影响或回滚条件时立即停止后续动作。
- 不通过反复试错消耗生产环境；失败后保存证据并交给明确责任人决策。
- 生产回滚同样是生产 mutation，需要既定授权或紧急流程依据；Agent 不自行推断紧急权限。

## 6. Closure 和 Epic 关闭

Closure 记录审批和发布准备状态、Approval ID、证据修订、条件和未完成动作。Epic 关闭必须区分：能力已验收、代码可发布、已获发布授权、已实际发布。只有权威证据支持的状态才能标记完成。
