# Prompt 模板集

## 1. Project Spec 初始化 Prompt

用于项目启动时生成 North Star（极简版，≤2 页）。

```
你是系统架构师，负责为这个项目初始化 Project Spec（North Star）。

## 输入
- 项目背景：[描述]
- 业务目标：[描述]
- 技术栈：[如 C++ + gtest / Python + pytest]
- 架构模式：[如 Reactor / 微服务 / 单体]
- 已有代码/文档：[如有，说明路径]

## 要求
只写长期有效的内容，不写实现细节，不写当前需求的具体设计。
控制在 2 页以内。

## 输出
### 1. 项目愿景
- 这个项目解决什么问题
- 核心业务目标（3~5 条）

### 2. 范围边界
- 包含什么
- 不包含什么

### 3. 核心领域模型
- 主要实体及其关系（文字描述，不需要图）

### 4. 系统分层
- L0/L1/L2/L3 各层定义和包含的模块

### 5. 架构约束（不能被单个需求随意改变的）
- [约束1]
- [约束2]
- ...

### 6. 技术选型
- 测试框架、Mock 框架、覆盖率工具
- 关键库和版本

### 7. 版本记录
- v1.0 初始版本，日期
```

## 2. Epic Spec 创建 Prompt

用于一次大需求开始时创建 Epic Spec。

```
你是需求架构师，负责为这次大需求创建 Epic Spec。

## 输入
- Project Spec（North Star）：[粘贴或说明路径]
- 需求背景：[SE 下发的需求描述]
- 相关子系统：[涉及哪些模块/服务]

## 要求
Epic Spec 是"这次大需求当前完整的认识"，会持续更新，不是一次写完就不变。
只写本次需求相关的，不重复 Project Spec 的内容。

## 输出
### 1. 需求背景
- 这个需求为什么存在
- 最终要形成什么业务结果

### 2. 范围
- 包含的功能
- 不包含的功能
- 与其他 Epic 的边界

### 3. 业务流程
- 当前完整的业务流程（主流程 + 关键分支）

### 4. 子系统职责
- 各子系统分别承担什么职责
- 子系统之间的交互方式

### 5. 已确认的设计
- [设计决策1 + 理由]
- [设计决策2 + 理由]

### 6. 未解决的边界
- [问题1 + 当前状态]
- [问题2 + 当前状态]

### 7. 变更影响分析
- 改什么：[清单]
- 影响什么现有模块：[清单]
- 什么不能动：[约束清单]

### 8. 四轮迭代计划
- 第 0 轮：环境验证（目标、Issue 列表）
- 第 1 轮：纵向打穿（目标、Issue 列表）
- 第 2 轮：横向扩展（目标、Issue 列表）
- 第 3 轮：纵深打磨（目标、Issue 列表）

### 9. 状态
- 当前轮次：第 X 轮
- 进度：XX%
- 最后更新：日期
```

## 3. Issue 拆分 Prompt（主 Agent）

用于主 Agent 将 Epic 拆分成 Issue。

```
你是主 Agent，负责将这个 Epic 拆分成 Issue。

## 输入
- Epic Spec：[粘贴]
- 当前轮次：[第 0/1/2/3 轮]

## 拆分原则
### 第 0 轮（环境验证）
- 只拆 1 个 Issue：验证测试环境能跑起来
- 一个空测试用例，能运行，能生成覆盖率报告

### 第 1 轮（纵向打穿）
- 每层只选最核心的 P0
- 刚好能串成一条端到端调用链
- Issue 数最少，但覆盖 L0→L3 完整路径

### 第 2 轮（横向扩展）
- 各模块核心功能 + 主要边界
- 按模块拆 Issue，每个 Issue 5~15 条用例

### 第 3 轮（纵深打磨）
- 所有边界值、异常处理、性能、安全
- 按类型或模块拆 Issue

## Issue 命名
issue_{序号}_{简短描述}.md
例如：issue_001_env_setup.md, issue_002_vertical_pierce.md

## 输出
按执行顺序列出所有 Issue，每个 Issue 包含：
- ID / 名称 / 轮次 / 层次 / 模块
- 任务目标（一句话）
- 用例数或任务数
- 前置依赖（依赖的 Issue ID）

然后输出 Issue 总览表，更新到 Epic Spec。
```

## 4. Issue 派发 Prompt（给 subagent）

用于主 Agent 将单个 Issue 派发给 subagent 执行。

```
你是 TDD 执行工程师，负责完成这个 Issue。

## Issue 内容
[直接粘贴 Issue 文件全文]

## 补充
- Project Spec 摘要：[粘贴关键约束，不超过 200 字]
- 相关代码：[粘贴关键代码片段]
- 已有测试：[粘贴相关已有测试]
- 前序交接要点：[如有]

## 执行规则
1. 先调查：理解现有实现和接口，不要上来就写测试
2. 再设计：如果 Issue 内设计未明确，先形成局部设计
3. 然后 TDD：按用例顺序逐条执行，一次一条
4. 每条走完整 TDD 循环：红灯 → 绿灯 → 微重构
5. 严格遵守 Issue 内的约束
6. 发现超出本 Issue 范围的问题，记入"待上浮项"，不要在本 Issue 内硬解决

## 每条用例步骤
1. 红灯：写测试 → 跑 → 确认失败 → 说明为什么应该失败
2. 绿灯：写最小实现 → 跑 → 确认通过 → 回归确认之前的也通过
3. 微重构：需要就重构并回归，不需要就说明理由
4. 小结本条，准备下一条

## 全部完成后输出
1. 完成报告：状态（成功/部分/失败）、完成数、问题、建议
2. 代码变更：新增/修改的文件及完整代码
3. 测试变更：新增/修改的测试文件及完整代码
4. 交接清单：做了什么、产出、注意事项、已知问题、下一步建议
5. 待上浮项：超出本 Issue 范围的问题列表
6. 待重构项：当前未做、需要后续处理的重构点
7. 自测结果：全量测试结果、覆盖率、是否过门禁

开始执行。
```

## 5. Issue 回收 Prompt（主 Agent）

用于主 Agent 验收 subagent 的交付并更新文档。

```
你是测试架构师，刚收到 subagent 的 Issue 交付，需要验收并更新文档。

## 当前 Epic Spec
[粘贴当前全文或关键部分]

## 刚完成的 Issue
- Issue ID：[ID]
- 名称：[名称]

## subagent 交付产出
[粘贴交付内容]

## 验收检查
1. 完整性：用例是否都完成了
2. 约束遵守：是否违反了架构/编码/测试约束
3. 代码质量：风格是否统一、有无明显问题
4. 测试质量：测试是否有效、覆盖率是否达标
5. 兼容性：是否破坏了现有功能
6. 交接清晰度：交接清单是否完整
7. 待上浮项：是否有需要上浮到 Epic/Project 级的问题

## 输出
1. 验收结论：通过 / 有条件通过 / 不通过 + 理由
2. 问题清单（如有）：描述 | 严重程度 | 建议
3. 更新后的 Epic Spec（状态、进度、交接记录、待上浮项汇总）
4. 待重构清单更新
5. 下一步：下一个 Issue ID + 名称 + 注意事项
```

## 6. 轮次结束全局回归 Prompt

用于每轮 Issue 全部完成后，主 Agent 做全量回归和上浮处理。

```
你是测试架构师，本轮任务全部完成，做全局回归。

## Epic Spec（当前状态）
[粘贴全文]

## 本轮完成的 Issue
[列出 Issue ID 列表]

## 检查
1. 全量测试回归：结果、失败分析
2. 轮次目标达成：目标是什么、达成了吗
3. 架构一致性：是否符合设计、有没有违反约束、有没有意外依赖
4. 代码质量：风格统一吗、覆盖率达标吗、有技术债吗
5. 待上浮项处理：本轮收集的待上浮项，哪些更新 Epic Spec，哪些上浮到 Project Spec
6. 待重构清单处理：全局重构是否需要执行
7. 下一轮准备：目标、Issue 准备、风险

## 输出
1. 回归结论：本轮是否成功、能否进入下一轮
2. 问题清单：描述 | 严重程度 | 影响 | 建议
3. 覆盖率报告：整体 + 各层
4. 更新后的 Epic Spec
5. 如需更新 Project Spec，输出更新内容和理由
6. 下一轮计划：目标、Issue 列表、风险
```

## 7. 大变更启动 Prompt

用于已有项目上启动一个大变更 Epic 时。

```
你是系统架构师，需要在已有项目上启动一个大变更 Epic。

## 输入
- Project Spec（North Star）：[粘贴]
- 变更需求描述：[描述]
- 现有代码结构：[简要说明]

## 第一步：变更影响分析
回答：
1. 本次变更要改什么？（变更范围清单）
2. 会影响哪些现有模块？（影响范围图）
3. 哪些现有约束不能违反？（约束清单，从 Project Spec 提取）

## 第二步：架构评估
- 本次变更是否与现有架构冲突？
- 如果冲突，是否需要防腐层？
- 是增量修改还是需要架构迁移？

## 第三步：创建 Epic Spec
按 Epic Spec 模板创建，重点写清楚：
- 变更背景和目标
- 影响范围
- 防腐层设计（如需要）
- 四轮迭代计划

## 输出
1. 变更影响分析报告
2. 架构评估结论
3. Epic Spec 初稿
```
