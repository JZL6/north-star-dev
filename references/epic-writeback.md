# Issue 回写 Epic 协议

执行 Issue 回收或基于已有 Issue 文档回写 Epic 时读取。单 Agent 自行完成核验与合并，多 Agent 由主 Agent 合并。沿用项目文档结构，不为套用本协议创建固定文件层级。

## 1. 触发与信息归属

Issue 关闭时完成回写核查；Issue 推进中出现状态变化、阻塞或重要设计发现时也应及时处理。不要等关闭后才上浮关键冲突。

回写分为两类：

- **状态同步**：同步 Epic 的关联 Issue 状态、证据、依赖和受影响验收条目。没有新设计认识也可能需要同步。
- **规格更新**：更新因新证据或已确认决策而变化的 Epic 目标、范围、业务流程、设计、约束、风险和开放问题。没有相关变化就保持这些内容不变。

Issue 没有关联 Epic 时不为回写创建 Epic；保留 Closure，按需要引用 Project 或 Baseline。

| 信息 | 权威位置 | Epic 中保留什么 |
|---|---|---|
| 局部实现过程、文件变更、完整测试日志 | Issue、Task 或 evidence | 需要追踪时保留链接 |
| 本次大需求的行为、验收、设计和边界 | Epic | 当前完整内容及依据 |
| 跨 Epic 的领域语义、架构原则或不变量 | Project Spec / ADR | 对相关约束的引用及本 Epic 的影响 |
| 指定源码修订上可验证的系统事实 | Baseline Manifest | 相关事实引用及对本 Epic 的影响 |

按作用范围判断，不按是否含函数名、文件名或数字判断。例如“断线后 5 秒内恢复”若为 Epic 的验收要求，应保留；局部重试变量的命名留在 Issue。Epic 仍须覆盖需求和业务流程，不能缩减为长期设计知识汇总。

## 2. 输入与按需核查

先读取目标 Epic 的相关条目及当前修订，再读取 Issue Closure。Closure 是摘要入口，不能单独证明实现符合要求。

| 内容角色 | 单文件 Issue 中的入口 | 已拆分文档中的入口 | 核查重点 |
|---|---|---|---|
| 最终结果、偏差、遗留项 | Light Change 的 Closure 区 | Closure.md，或 Issue.md 中的 Closure | 做成什么、未做成什么、发生什么变化 |
| 需求与行为增量 | 目标、约束、验收计划 | Delta-Spec.md 或同等文档 | 能力、范围、业务流程、验收变化 |
| 最终设计 | 局部设计、上浮项 | Delta-Design.md 或同等文档 | 最终决策、适用范围、被取代方案 |
| 实现与验证 | 执行证据 | Task.md 总结、报告或 evidence | 实现偏差、实际修订、验证结果 |
| 安全、隐私与风险接受 | Light Change 的 Gate/Closure | Security Review、Verification、Approval Matrix | 适用性、长期控制、残余风险、有效审批 |
| 发布状态 | Light Change 的 Approval/Release | Approval Matrix、release evidence | 代码验收、发布准备、发布授权、实际发布分别核查 |

读取顺序是查找策略，不是权威排序。只先读取相关章节；证据缺失、过期或冲突时再沿链接读取必要的设计、源码、diff 和测试。不得因为文件名或摘要限制禁止必要核查。

Closure 缺失时，从现有结果和证据整理最小 Closure，标记证据缺口。轻量变更允许在一个 Light Change 文件中维护全部逻辑章节；标准或完整档位使用独立 Closure.md。无法核实的结果保留为待核查，不能根据 Task 勾选完成就推断 Issue 已验收。

区分两种依据：用户要求和已授权决策决定“应当如何”；代码与测试说明“实际如何”。两者不一致是待处理偏差，不能自动选择实现覆盖要求。

## 3. 提取与判定

对比原有 Epic 条目与 Issue 最终结果，形成有稳定 ID 的回写候选。每条记录目标、旧认识与新认识、理由、来源证据、适用修订和受影响 Issue。纯状态更新也可以作为一条候选；无变化时在 Closure 写明无需更新，不创建空候选表行。

对每项偏差或新结论判定：

| 情况 | 处理 |
|---|---|
| 符合原规格，只有实施进度变化 | 同步状态和证据；不重写设计 |
| 局部细节变化，不影响 Epic | 留在 Issue，记录无需规格更新 |
| 已获授权的范围或设计调整 | 核对决策来源后更新相应 Epic 条目 |
| 实现不符合规格 | 记录缺陷、未满足验收或修复 Issue；不能改规格掩盖偏差 |
| 新的范围扩展或验收放宽，尚未批准 | 作为提案或开放问题，按既有权限边界等待决策 |
| 证据互相矛盾或不适用于当前修订 | 标记冲突并核查；暂停依赖该结论的更新 |
| 项目级原则或契约变化 | 按上浮规则先完成相应决策，再更新权威资料和 Epic 引用 |

代码已实现、测试已通过均不能替代范围变更授权。既有用户授权或项目决策已充分覆盖的调整可直接执行，不重复索取确认。

设计决策状态与实现验证状态分开记录。已采纳但未实现的设计可以进入 Epic；验证失败不自动撤销该设计，也可能需要修复实现。反之，已实现且验证通过的行为可能尚未获得需求层面的认可。

## 4. 应用与反馈

1. 主 Agent 核查候选对应的证据、授权和当前 Epic 版本；必要时运行相关验证，不因纯文档回写无条件重复全量测试。
2. 按目标 ID 更新已有条目。开放问题解决时更新原条目的状态与依据；设计取代旧决策时保留可追踪的取代关系。
3. 同步 Issue 状态与验收证据。判断 Requirement 是否满足时核查该条目的全部验收条件和相关依赖，不能从一个 Issue 的 accepted 状态直接推导。
4. 规格变化影响后续工作时，重新检查开放 Issue 的目标、验收、依赖、契约和 Context Pack，并记录需刷新或暂停的对象。
5. 在 Epic 保留精简的来源 Issue、候选 ID 和证据链接，在 Closure 记录已应用的位置及结果。长推理和过程日志留在 Issue/evidence。
6. 安全/隐私长期事实按作用范围回写，保留数据分类、信任边界和控制的权威来源；不复制 secret、个人信息或敏感样本。
7. 范围/验收豁免、残余风险和发布状态只在有效 Approval ID 覆盖当前范围与修订时更新。Review/Test PASS 不能替代审批，代码验收不能写成已发布。

Issue 工作状态与回写状态分别维护：实现通过但回写未完成时，明确记录“已验收、对账待完成”。阻塞性的范围、验收或设计冲突未解决时，不能宣称对应工作已验收。该 Issue 的回收对账只有在应处理候选已有明确处置、受影响条目已同步后才算结束。

## 5. 重复执行与恢复

- 候选 ID 在同一 Issue 内稳定，例如 `WB-001`；与 Issue ID 合用成为唯一标识。同一修订重新处理时沿用该标识。
- 记录读取时的 Epic 文档修订、证据源码修订和适用的文档/报告版本。没有 Git commit 时使用内容摘要或不可变快照标识；不要把输入 baseline revision 当成完成实现的修订。
- 应用前重新核对目标条目。若其他工作已改变它，重读并重新判定，保留无关改动，不覆盖为旧快照。
- 每条候选使用 `pending | applied | no_change | needs_decision | conflict`。无变化也记录理由；`applied` 需包含目标位置和证据。
- 如果 Epic 已更新而 Closure 还没标记，恢复时按候选 ID、目标内容与证据核对，补齐记录，不重复追加。
- 如果 Closure 标为 applied 但目标不存在或已冲突，重新核查并标记冲突，不能仅信任完成标记。
- 没有新事实、状态或证据时，重复执行不得追加重复决策、重复来源、变更记录或仅刷新日期。

## 6. 最小例子

Epic 要求断线重连；Issue 完成既定重试行为，但没有产生新设计：同步 Issue 状态和相应证据，核查验收覆盖，记录无需规格更新。

Issue 实现时加入“统一连接生命周期管理”，但原授权仅覆盖断线重连：记录范围扩展提案及影响，保留正式范围，按已有决策权限处理。即使新增行为的测试通过，也不能自行把 Epic 目标扩大。

Issue 发现“重试调度归属”这个开放问题已通过已有授权的设计决策解决：更新原问题和决策条目，链接证据，刷新依赖该结论的 Issue。设计若仍未实施，验证状态保留 not_verified。
